# Wire golden corpus v1 and schema-aware codecs — design

Date: 2026-11-02. Third oracle, after the regression suites and the on-disk corpus.

## Intent

During the migration, Rust processes will run in mixed clusters with the Java FE and the C++
BE, so every internal RPC must be byte-compatible. This corpus records real FE↔BE traffic from
the 4.1.5 reference; Rust codecs must decode every captured message with the reference's own
schema and re-encode it to the identical bytes. A message that decodes but re-encodes
differently means the Rust schema or codec disagrees with the reference.

## Goals

- Capture, on a freshly started reference, the internal RPC traffic of a scripted scenario:
  BE registration and heartbeats, reports, DDL that creates and drops tablets, INSERT, SELECT,
  stream load.
- Store every complete RPC message: Thrift calls and replies on 9020 (FrontendService), 9050
  (HeartbeatService), 9060 (BackendService), and gRPC requests and responses on 8060
  (PBackendService), with method, direction, and sequence id or stream id.
- Rust: decode every captured Thrift message with types generated from the pinned IDL and
  re-encode it byte-for-byte; decode every captured gRPC payload with prost types from the
  pinned protos and re-encode it byte-for-byte; decode the compact-protocol Thrift plan nested
  in `exec_plan_fragment` requests and re-encode it byte-for-byte.

## Non-goals (v1)

MySQL protocol (9030), HTTP bodies (stream load), brpc `baidu_std` between BEs (needs the
multi-node profile), Arrow Flight, TLS, and implementing any service.

## Reference facts (4.1.5, verified)

- FE↔BE Thrift is `TBinaryProtocol`, strict, unframed: FE `thrift_server_type = THREAD_POOL`,
  BE `thrift_server_type_of_fe = THREAD_POOL`, BE backend and heartbeat servers buffered.
  Message boundaries exist only in the protocol itself, so a connection is only splittable from
  its first byte: streams whose SYN was not captured are dropped.
- FE→BE `PBackendService` is gRPC (`io.grpc` channel) over HTTP/2 to the BE brpc port; header
  decoding (HPACK) needs the connection from its start, which tshark 4.6 handles.
- `PExecPlanFragmentRequest.request` holds a `TPipelineFragmentParamsList` serialized with
  `TCompactProtocol` (observed bytes `19 1c 15 00 ...`).
- Thrift 0.24.0 (`--gen rs --allow-64bit-consts`) generates all 27 IDLs (4.1 MB of Rust) that
  compile against the `thrift` 0.25 crate after one patch (a union list boxed in
  `parquet.rs`). Per-method `*Args`/`*Result` structs are private and must be exposed; each
  service processor's `match` maps wire method names to them.
- prost encodes fields in tag order, as the C++ and Java protobuf serializers do.

## Decisions

- Capture: `oracle/compose/capture.yml` adds a `capture` service (`nicolaka/netshoot:v0.16`,
  `network_mode: service:doris`, tcpdump on `lo`) started immediately after the reference
  container, before the FE has booted. The pcap stays untracked; the extracted messages and
  manifest are the committed corpus under `oracle/wire/corpus/`.
- Extraction: tshark (same image) exports TCP segments and gRPC message data; Python
  reassembles each stream by sequence number and splits Thrift with a schema-less
  `TBinaryProtocol` skipper.
- Crates: `doris-proto` (prost, single home of the pinned `.proto` copies; `doris-segment`
  depends on it), `doris-thrift` (generated code committed, regenerated by a script that runs
  the pinned compiler in the runner image and applies recorded patches), `doris-wire`
  (corpus access and conformance tests).
- Generated Thrift code is committed rather than built: the compiler exists only in the runner
  image, and upstream has deprecated its Rust target, so a home-grown generator may replace it
  later.

## Left to the builder

The exact scenario statements (they must produce at least: heartbeat, report, submit_tasks,
finishTask, reportExecStatus, exec_plan_fragment and fetch_data, and the stream-load
transaction calls), file naming inside the corpus, and the dispatch table's shape.
