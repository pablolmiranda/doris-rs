## 1. `regexp` (alias `rlike`)

### Registration, types, NULLs
- `FunctionRegexpLike` (`exprs/function/like.h:425-435`) has name `regexp` and alias `rlike`
  (`like.cpp:1108-1111`). Its return type is `UInt8` (BOOLEAN, `like.h:288-290`).
  `use_default_implementation_for_nulls` is **not** overridden, so it is the default: a NULL
  value or a NULL pattern gives NULL. The function still runs on the nested (default) data of
  NULL rows. That matters for errors (see "per-row" below).
- The result column is pre-filled with 0, and matchers only set 1 (`like.cpp:609-611`).

### Open (prepare) — `FunctionRegexpLike::open`, `like.cpp:1038-1101`
Runs per THREAD_LOCAL. It reads `enable_hyperscan_fallback` and `enable_extended_regex`
(`:1046-1048`). The defaults are `function = regexp_fn` and `scalar_function = regexp_fn_scalar`.
**If the pattern (arg 1) is constant**, it classifies it with RE2 `FullMatch` in this order:

| regex (`like.cpp:41-54`) | result | matcher |
|---|---|---|
| `ALLPASS_RE = (\.\*)+` | all rows true | `constant_allpass_fn` |
| `EQUALS_RE = \^([^.^{[(\|)\]}+*?$\\]*)\$` | value == literal | `constant_equals_fn` |
| `STARTS_WITH_RE = \^(lit)(?:\.\*)*` | prefix | `constant_starts_with_fn` |
| `ENDS_WITH_RE = (?:\.\*)*(lit)\$` | suffix | `constant_ends_with_fn` |
| `SUBSTRING_RE = (?:\.\*)*(lit)(?:\.\*)*` | substring (`""` matches all) | `constant_substring_fn` |
| otherwise | **Hyperscan** | `constant_regex_fn` |

`lit` is `[^\.\^\{\[\(\|\)\]\}\+\*\?\$\\]*`. So `-`, `#`, space, `&`, `%` and `_` count as
literals, and so do multi-byte UTF-8 characters, because the classifiers are RE2 in UTF-8 mode.
These shortcuts give the same answer as a regex search. The one exception is a pattern holding
bytes that are not UTF-8: the classifier does not match it, it falls through, and the compile
fails.

Otherwise (`:1078-1099`): `hs_prepare(pattern_str.c_str())` (`:561-592`):
- `is_hyperscan_regexp_expensive` (`util/hyperscan_util.cpp`) is true when a `{n}`, `{n,}` or
  `{n,m}` has a number greater than 50 (searched with `\{\s*(\d+)\s*,?\s*}` and
  `\{\s*(\d+)\s*,\s*(\d+)\s*\}`). In that case Hyperscan is skipped with
  `RuntimeError("Skip hyperscan compilation because bounded repetition exceeds 50")`.
- `hs_compile(expr, HS_FLAG_DOTALL | HS_FLAG_ALLOWEMPTY | HS_FLAG_UTF8, HS_MODE_BLOCK)`. There
  is **no HS_FLAG_UCP and no CASELESS**. The pattern is the C string, so **an embedded NUL
  truncates it**.
- If Hyperscan fails and `enable_hyperscan_fallback` is false, the hs status is returned. The
  corpus always sends true. If it is true: `compile_regex(pattern_str, enable_extended_regex)`.
- Errors here fail at **open/prepare**, even if no rows arrive.

### `compile_regex` — `like.cpp:509-539` (RE2, then Boost)
- RE2 options: `never_nl=false`, `dot_nl=true`, `log_errors=false`. Defaults are kept: UTF-8,
  case-sensitive, Perl classes on, `longest_match=false`.
- RE2 fails and extended is off:
  `Status::InternalError("Invalid regex expression: {pattern}. Error: {re2 error}. If you need advanced regex features, try setting enable_extended_regex=true")`
  (`:522-527`). The status code is **INTERNAL_ERROR**, with a stack trace
  (`common/status.h:55`).
- RE2 fails and extended is on: `boost::regex(pattern)` with the default (Perl/ECMAScript)
  flags. If Boost also throws:
  `InternalError("Invalid regex expression: {pattern}. Error: {boost what()}")` (`:533-537`).
  There is no hint suffix, and the RE2 error is not included.
- RE2 2021-02-02 error texts seen in this repo's suites: lookbehind or a named group `(?<…` →
  `invalid perl operator: (?<`
  (`regression-test/suites/external_table_p0/dialect_compatible/sql/presto/scalar/AbstractTestRegexpFunctions.sql:35`).
  By the same parser rule, lookahead → `invalid perl operator: (?=` and `(?!`.
  Unmatched `(` → `missing ): (`. These last two are from RE2's `kRegexpMissingParen` /
  `kRegexpBadPerlOp` texts and are not checked against a live BE.
- This RE2 version does **not** support `(?<name>…)`, only `(?P<name>…)`. The Rust `regex`
  crate accepts both, so `(?<name>` must be turned into the RE2 error.

### Matching — `regex_search`, `like.cpp:541-554`
- RE2: `RE2::PartialMatch(val, re)`, an **unanchored search**: `^`/`$` anchor only at text
  ends, and `.` matches `\n`.
- Boost: `boost::regex_search(begin, end, re)` with `match_default`. If it throws
  (`error_complexity` / `error_stack`):
  `InternalError("Failed to match regex expression: {re.str()}. Error: {what()}")` (`:543-550`).
- Hyperscan: `hs_scan`. The callback sets 1 and stops at the first match (`like.h:224-232`). A
  scan error gives `RuntimeError("hyperscan error: {n}")` (`:421-427`, `:450-458`).

### Per-row (non-constant) pattern — `vector_non_const`, `like.cpp:701-735`
1. `pattern_type_recognition<false>(patterns)` (`:633-699`) runs the same five classifiers over
   **every row's nested pattern**, including NULL rows, whose nested value is normally `""`. An
   empty pattern fits SUBSTRING (not ALLPASS: `(\.\*)+` needs at least one `.*`).
   - If **every** row fits one class, it runs one vectorised literal matcher. The priority is
     allpass > equals > substring > starts > ends.
   - Otherwise it calls `regexp_fn_scalar` (`:435-444`) per row: a fresh **RE2** compile, then
     Boost if extended is on. **Hyperscan is never used per row.**
2. A compile error on **any** row fails the whole query. This includes rows whose value is
   NULL: row 6 of the extended suite (`s` NULL, `p = 'foo(?=123)'`) makes the query fail when
   extended is off.

### What the suites check
- `test_like_predicate_with_concat` sql9 `'^prefix'` → STARTS_WITH. sql10 `'.*suffix.$'` →
  Hyperscan (the literal part contains `.`). sql13-15 are per-row: row 6's pattern contains `^`,
  so the recognition fails and each row goes through RE2. A mid-pattern `^` never matches. sql16
  `'prefix0_infix0_suffix0'` → SUBSTRING. Row 9 (pattern NULL) → NULL, filtered out.
- `test_regexp_chinese`: `"^上海｜^北京"`. The bar is the **full-width U+FF5C**, not `|`, so the
  pattern is a literal followed by a mid-pattern `^`, which never matches. The expected result
  is empty. Path: classifiers fail (`^` inside) → Hyperscan.
- `test_regexp_extended_nonconstant_pattern`:
  - With extended=true: the constant `(?<=foo)bar` / `foo(?=123)` go Hyperscan (unsupported) →
    RE2 (rejects) → Boost. Column `p` goes per row through RE2, then Boost.
  - `s REGEXP substr(p,1,1)` on id=1 → pattern `(` → error containing
    `Invalid regex expression: (` (the Boost message).
  - `repeat('a',60) REGEXP concat('', '(?=a)(a+)+b')` → Boost's `error_complexity` → error
    containing `Failed to match regex expression`. The suite asserts only these substrings.
  - With extended=false: both the per-row and the constant case fail with the hint suffix
    (`try setting enable_extended_regex=true`). The constant case fails at open.
  - Expected results: lookbehind, lookahead and `^foo` work as in Perl. NULL value or NULL
    pattern → `\N`. `NOT s REGEXP p` drops the NULL rows.

### Engine semantics that matter for a reimplementation
- **Hyperscan (constant, unclassified)**: PCRE syntax, `.` matches any code point (DOTALL,
  UTF-8). Without UCP, `\w \d \s \b` are ASCII. `\p{…}` is supported. There are no
  backreferences and no arbitrary zero-width assertions (it fails, and falls back to RE2). The
  docs list `\A \Z \z $` but do not define `$` before a trailing newline. Hyperscan claims PCRE
  semantics, where `$` (non-multiline) **also matches before a final `\n`**. Treat that as
  likely and unverified. Hyperscan expects valid UTF-8 input in UTF-8 mode; invalid input is
  undefined behaviour. Caseless `(?i)` with non-ASCII under UTF-8 without UCP is unverified.
- **RE2** (per-row, and constant fallback): `$` = end of text only. `\w \d \s \b` are ASCII.
  RE2's `\s` is `[\t\n\f\r ]`, **without `\v`**. `(?i)` uses Unicode simple case folding.
  `\C`, `\pN` and `\Q…\E` are supported. Repeat counts above 1000 → `bad repetition operator`.
  No lookaround, no backreferences.
- **Boost 1.81** (extended fallback): byte-oriented on `char`, so `.` and `[^x]` consume
  **one byte**, not one UTF-8 character. `.` matches `\n` by default. In Perl mode `^`/`$`
  **match at line boundaries by default** (no `match_single_line`). `\w` etc. come from the C
  locale, so ASCII. Backtracking has a state budget (`perl_matcher::estimate_max_state_count`,
  roughly `max(states² · len + 100000, min(len² + 100000, 1e8))`); going over it throws
  `error_complexity`. Its `what()` is (from Boost's default error strings, not checked here)
  `The complexity of matching the regular expression exceeded predefined bounds.  Try refactoring the regular expression to make each choice made by the state machine unambiguous.  This exception is thrown to prevent "eternal" matches that take an indefinite period time to locate.`
  A parse error message is `<error string>  The error occurred while parsing the regular expression: '<prefix>>>>HERE>>><suffix>'.`
  (unverified for `(`).

## 3. `eq_for_null` (`<=>`)

- `FunctionEqForNull` (`exprs/function/comparison_equal_for_null.cpp:52-315`): it returns a
  non-nullable UInt8 and sets `use_default_implementation_for_nulls=false`.
- Semantics, row by row: both NULL → **true**; exactly one NULL → **false**; neither NULL → the
  ordinary `eq` result.
  - An all-NULL-literal side gets the shortcuts at `:91-145`.
  - For two nullable columns, `_exec_nullable_equal` computes `(l_null == r_null) & (l_null | eq)`
    (`:301-313`).
  - When only one side is nullable, it runs `eq` with a nullable result and masks NULL to 0
    (`:244-294`).
- `eq` itself is resolved from the factory by argument types (`:197-201`), so type-specific
  equality is the ordinary `eq`.
- The FE sends it as a BINARY_PRED with `opcode = EQ_FOR_NULL (65)`
  (`fe/.../analysis/BinaryPredicate.java:57`, `ExpressionTranslator.java:287-295`, always
  not-nullable). In doris-rs, `comparison()` (`eval.rs:141-147`) must map opcode 65 (or
  fn `eq_for_null`) and must not use NULL-propagating evaluation.

## 4. `concat_ws`

- FE signatures (`fe/.../functions/scalar/ConcatWs.java:40-50`):
  - `VARCHAR(VARCHAR sep, ARRAY<VARCHAR>)`
  - `VARCHAR(VARCHAR sep, VARCHAR...)`
  - `STRING(STRING sep, STRING...)`
  - varargs over arrays (compatibility)
  - `STRING(STRING, ARRAY<STRING>...)`

  **Nullable = the separator's nullability** (`:67-70`).
- BE: `FunctionStringConcatWs` (`exprs/function/function_string_concat.h:349-566`). The return
  type is `String`, nullable iff arg 0 is nullable. `use_default_implementation_for_nulls=false`.
  - **NULL separator → NULL row**: the null map is copied from arg 0 and an empty value is
    written.
  - **NULL string args are skipped entirely**: no separator is added for them.
  - Empty strings are kept, so `concat_ws('_','a','','b') = 'a__b'`.
  - With all args NULL the result is `''`, not NULL.
  - Output = the non-NULL args joined with `sep` (`fmt::join`), byte for byte. There is no
    UTF-8 handling.
- Array form: exactly 2 args, otherwise `InvalidArgument("concat_ws with array argument
  expects exactly 2 arguments, but got {n}")`.
  - NULL elements are skipped.
  - A NULL array row → `''` (empty string, not NULL).
  - A NULL separator → NULL.
  - A non-string nested type → `NotSupported`.
  - Not used by these suites; refuse it unless arrays are already supported.
- Suites: `concat_ws('_', pid_code, gid_code, account)`, with all three args non-nullable
  STRING slots → VARCHAR. This is simple.

## 6. Rust implementation advice

### Shared plumbing
- `regexp` needs `enable_extended_regex` (TQueryOptions 177) and `enable_hyperscan_fallback`
  (228) wherever expressions run. A thread-local set next to `with_clock` (`clock.rs`) fits.
  **Refuse `enable_hyperscan_fallback = false`** whenever a constant regexp pattern would reach
  Hyperscan, because doris-rs cannot predict Hyperscan's compile failures.
- Compile constant `regexp` patterns at **prepare/open**, not per block. C++ fails at open even
  with zero rows. Today's `like` path returns early on `rows == 0`.
- Status codes: compile and match errors → `INTERNAL_ERROR`, using the existing
  `ExecError::Internal`, as `like` does. `assert_true` → `ExecError::Coded` with
  `INVALID_ARGUMENT` and message `[E33] {msg}`.

### `regexp` engine choice
The workspace already has `regex = "1"` (1.13), used by `strings.rs` for `like` with
`regex::bytes`, `unicode(true)` and `dot_matches_new_line(true)`. Use it for the RE2 and
Hyperscan paths, behind a **regex-syntax AST gate** (`regex-syntax` 0.8 is already in the lock
file through `regex`). Parse with `regex_syntax::ast::parse::Parser` and accept only a subset
where `regex` = RE2 = Hyperscan:

- **Accept**:
  - literals, including UTF-8 multibyte
  - `.`
  - `^` and `$`, with the `$` caveat below
  - bracket classes with ranges and negation
  - POSIX `[[:alpha:]]` (ASCII in all three)
  - groups `( )`, `(?: )`, `(?P<n> )`
  - alternation
  - quantifiers `* + ? {n} {n,} {n,m}` and their lazy forms, with n, m ≤ 1000
  - escapes of punctuation, `\t \n \r \f \v \xHH`, `\A`, `\z`
  - `\p{…}` (the Unicode version can differ slightly; acceptable, or refuse)
- **Rewrite**: `\d \w \b \B` → their ASCII forms (`(?-u:\w)` etc., valid in `regex::bytes`).
  Rust's Unicode-mode `\w`/`\d`/`\b` are Unicode and would differ on non-ASCII data. Rewrite
  `\s` → `[\t\n\f\r ]` (RE2's set). On the Hyperscan path `\s` probably includes `\v`, so refuse
  `\s` on the constant path, or accept it and document the difference.
- **Refuse** (an error naming the feature):
  - `(?i)` on the constant/Hyperscan path (its case folding is unverified). On the per-row RE2
    path Rust and RE2 both use simple Unicode folding, so it is acceptable there.
  - `\C`, `\Q…\E`, `\Z`, octal or `\0` escapes, `(?<name>…)` (RE2 2021 rejects it: emit RE2's
    error rather than refusing), the flags `m`, `s`, `U`, `x`, and anything else not listed.
  - Non-UTF-8 patterns.
  - On the constant path, a NUL in the pattern (Hyperscan truncates it), as `like` already does.
- **Constant path and `$`**: if Hyperscan's PCRE `$` really matches before a final `\n`,
  `'.*suffix.$'` differs only for values ending in `\n`. Either refuse at runtime when a
  Hyperscan-path pattern containing `$` meets a value ending in `\n`, or rewrite a trailing `$`
  as `(?:\n?\z)`. The rewrite is only safe when `$` ends the pattern or a top-level branch.
  None of the suite data contains `\n`.
- Classify first, exactly like C++. Port `ALLPASS/EQUALS/STARTS/ENDS/SUBSTRING_RE` (they differ
  from the LIKE classifiers already in `strings.rs`), both for constants and for the all-rows
  recognition. The answers match regex search anyway, but the order decides which patterns reach
  the regex compiler, and so which errors appear.
- Per-row: compile each row's pattern, NULL-value rows included, in row order, and return the
  first error. Treat a NULL pattern as `""`, matching `like_column`. Cache compiled patterns per
  distinct string.
- Error text for RE2 rejects: reproduce RE2 2021's `error()` strings for the cases the gate
  reports:
  - `invalid perl operator: (?<`, `invalid perl operator: (?=`, `invalid perl operator: (?!`
  - `missing ): …`, `missing ]: …`, `unexpected ): …`
  - `bad repetition operator: …`, `missing argument to repetition operator: …`
  - `invalid escape sequence: …`, `invalid character class range: …`

  RE2's argument is the offending suffix or token. Anything the gate rejects that has no known
  RE2 text should be **refused** rather than given an invented message.

### Boost path (`enable_extended_regex = true`, RE2 rejects)
- No crate matches Boost byte for byte. `fancy-regex` (not in the workspace) supports lookaround
  and backrefs and has a backtrack limit (`BacktrackLimitExceeded`, default 1e6). But it works on
  `&str`, is Unicode-aware, delegates non-fancy sub-expressions to `regex` (linear time, so it
  may **not** raise where Boost does), and its limit differs from Boost's state budget.
- Options:
  1. Accept a narrow subset and implement a small byte-wise backtracker that mirrors Boost's
     `perl_matcher` budget. This is high effort, and the state-count formula depends on Boost's
     internal program size, so the error boundary is approximate.
  2. Use fancy-regex with an ASCII-only gate:
     - the pattern is ASCII
     - lookaround only in the forms `(?=…)`, `(?!…)`, and fixed-length `(?<=…)`, `(?<!…)`
     - no `^`/`$` (Boost's multiline anchors) unless the value has no `\n`; check per value at
       runtime
     - values must be valid UTF-8 and ASCII wherever `.` or a negated class could consume a
       non-ASCII byte (check per value)
     - **refuse nested unbounded quantifiers** (`(x+)+`, `(x*)*`, …), because the
       complexity-error boundary cannot be matched

     With option 2 the suite's `(?=a)(a+)+b` case is refused, so the
     `exception "Failed to match regex expression"` block fails unless the refusal text contains
     that phrase. It must not: a refusal names the feature. This one test block is the main open
     risk of the batch. The other blocks pass with option 2: lookbehind and lookahead results,
     `(` → Boost parse error starting with `Invalid regex expression: (. Error: `, and the
     extended=false errors with the hint.
- The Boost `what()` texts are not verified (Boost sources are not in `.cache`). Only the
  prefixes `Invalid regex expression: {p}. Error: ` and `Failed to match regex expression: {p}. Error: `
  come from Doris itself.

### `to_date`, `concat_ws`, `eq_for_null`, `assert_true`
- `to_date`: accept only `DATETIMEV2 → DATEV2`. `Datum::Int(v) → Datum::Int(v >> 37)`, NULL →
  NULL.
- `concat_ws`: accept text args. Refuse array args unless arrays exist. NULL separator → NULL,
  NULL args skipped, the return type's nullability taken from `TExprNode`.
- `eq_for_null`: BINARY_PRED opcode 65. Evaluate both sides, then (both NULL → true, one NULL →
  false, else the existing `eq`). The result is non-nullable. Reuse whatever type coverage `eq`
  already has, and refuse the rest.
- `assert_true`: arg 1 must be a string literal, else refuse (C++ fails at open with
  `InvalidArgument`; the FE always sends a literal). Over the evaluated block: if any row is
  NULL or false → `Coded{INVALID_ARGUMENT, "[E33] {msg}"}`; otherwise a column of true.

## 7. Risks (summary)
1. **Boost complexity error** (extended suite, last block): it cannot be matched exactly without
   re-implementing Boost's backtracker budget.
2. **Unicode vs ASCII Perl classes** in `regex`: `\w \d \s \b` must be rewritten, or patterns
   with them will silently differ on non-ASCII data.
3. **Hyperscan `$` before a final newline** and its `(?i)`/`\s` details (unverified) on the
   constant path.
4. **Error text fidelity**: RE2 2021 messages and Boost `what()` strings. The suites check only
   substrings, but replies must be byte-identical.
5. **Open-time errors**: constant regexp compile errors must surface at prepare, even for empty
   inputs.
6. **NULL-row nested patterns**: C++ compiles the nested value of NULL pattern rows (normally
   `""`). An upstream function that leaves non-default garbage in NULL rows could raise in C++
   but not in Rust. This is unlikely in these suites.
