# Batch 5 research: date rounding, epoch conversions, interval strings, formatting, zones

C++ root: `.cache/doris-src/be/src` (tag `4.1.5-release`, the same release as the reference image
`apache/doris:all-in-one-4.1.5`). Paths below are relative to `be/src/exprs/function/` unless they start
with `core/` or `util/`. Value layouts as in doris-rs `datetime.rs` (`Dt::unpack`/`pack`):
DATEV2 u32 = `y<<9 | m<<5 | d`; DATETIMEV2 u64 = `y<<46 | m<<42 | d<<37 | h<<32 | mi<<26 | s<<20 | us`.
`DTV2(s)` = DATETIMEV2 scale s; `?` = nullable.

**Status in doris-rs:** none of the listed functions exist yet (`datetime::supported`/`is_date_function`
cover `year month dayofmonth weekofyear yearweek days_diff weeks_diff str_to_date` and the
`{years..seconds}_{add,sub}` family). Reusable pieces: `calc_daynr`, `date_from_daynr`, `is_leap`,
`days_in_month`, `add(unit, ..)` (YEAR/MONTH/WEEK/DAY/HOUR/MINUTE/SECOND with C++'s range checks),
`calc_week`/`mysql_week_mode`, `str_to_date`'s `from_date_format_str` port; `clock::find_zone`
(= `TimezoneUtils::find_cctz_time_zone`), `clock::instant` (= `cctz::convert(civil, zone)`, i.e. the
`pre` instant), `clock::local`, `clock::current()` (the query zone). Error codes as already used:
OUT_OF_BOUND → `ExecError::Coded{code: -218, name: "E-218"}`, INVALID_ARGUMENT → `{code: 33, name:
"INVALID_ARGUMENT"}`.

Error-message dates use `DateV2Value::to_string` (scale −1): `YYYY-MM-DD` for DATEV2,
`YYYY-MM-DD hh:mm:ss` for DATETIMEV2 plus `.ffffff` (always 6 digits) only when µs ≠ 0.

**Where errors surface.** As established in batch 2 (`2026-11-10-m6-s7b2-dates-bits.md`): an all-literal
call is evaluated at fragment open, so its throw fails the **exec_plan_fragment** reply; a call over a
column fails on fetch. In addition, functions with an `open()` that reads constant arguments
(`date_format`, `from_unixtime*`, `convert_tz`) throw from open — i.e. at exec_plan_fragment — even when
the first argument is a column (bad format/zone constant).

**How the suites reach the BE.** Nereids folds all-literal expressions in the FE, so plain
`qt_x "select f('lit', ...)"` never reaches the BE. The BE evaluates literals only when the session has
`debug_skip_fold_constant=true`: either explicitly (`sql "set debug_skip_fold_constant=true"`, or the
hint `/*+ SET_VAR(debug_skip_fold_constant = true) */`), or through the framework's `testFoldConst(sql)`
(`regression-test/framework/.../Suite.groovy:2422-2441`): it runs the query with
`debug_skip_fold_constant=false`, then with `=true`, and asserts both results are equal (no `.out`
entry) — so for every `testFoldConst` the BE result must equal the FE fold. `check_fold_consistency`
(test_months_between) is the same idea. Queries over table columns always reach the BE.

## 1. `{year,quarter,month,week,day,hour,minute,second}_{floor,ceil}`

`function_datetime_floor_ceil.cpp` (class `FunctionDateTimeFloorCeil` :124-300, core
`DateTimeFloorCeilCore` :303-848, registration :968-1013).

### Signatures (FE `nereids/.../scalar/YearFloor.java` etc.)
For each name: `(T)`, `(T, T origin)`, `(T, INT period)`, `(T, INT period, T origin)` with `T` =
DATEV2 or DATETIMEV2(s) (WILDCARD: arg and return share the scale), return `T`. (TIMESTAMPTZ variants
exist; not needed.) FE casts string literals to DATETIMEV2 with the scale of the text
(`'2025-09-10 12:34:56.123'` → DTV2(3)); `cast(dt as date)` gives the DATEV2 forms.

### NULL handling
`use_default_implementation_for_nulls() = false`. Result null map = OR of all argument null maps; the
result is Nullable iff the planned return type is. Null rows are skipped (no computation, no error).
If **every** row is null (and rows > 0) it returns all-NULL before validating the period (:178-186).

### Period validation
Constant period (INT, not NULL) `< 1` → throws before the loop:
`Operation hour_floor of 0 out of range` (`throw_out_of_bound_int`, :212-226, :251-261).
Non-constant period: per row, `period < 1` → the per-row message (below). Suite: `hour_floor(dt,0)`
over table rows → `exception "out of range"`.

### Algorithm (`time_round_two_args`, :646-781) — port this, ignore the "optimized" path
`res` starts as the origin (default origin `FIRST_DAY` = `0001-01-01 00:00:00`, :1496 of
`core/value/vdatetime_value.h`). The optimized `floor_opt` path (:782-848, FLOOR only, period dividing
the unit cycle) gives identical answers to the generic path with origin 0001-01-01, so implement only
the generic one:

1. `diff` and two "trivial parts" (the sub-unit remainder of arg `a` and origin `o`), **for DATETIMEV2**
   (packed `v`):
   - YEAR: `diff = a.y − o.y`; trivial = `v & ((1<<46)−1)` (month..µs).
   - QUARTER: `diff = (a.y − o.y)*4 + (a.m − o.m)/3` (**C truncating division**, may be negative);
     trivial = `((m−1)%3) * (1<<42) + (v & ((1<<42)−1))`.
   - MONTH: `diff = (a.y − o.y)*12 + (a.m − o.m)`; trivial = `v & ((1<<42)−1)` (day..µs).
   - WEEK: `diff = daynr(a)/7 − daynr(o)/7`; trivial = `((daynr%7)*86400 + h*3600 + mi*60 + s)*1e6 + us`.
   - DAY: `diff = daynr(a) − daynr(o)`; trivial = `v & ((1<<37)−1)` (h..µs).
   - HOUR: `diff = (daynr(a)−daynr(o))*24 + (a.h − o.h)`; trivial = `v & ((1<<32)−1)` (mi..µs).
   - MINUTE: `diff = ((daynr diff)*24 + h diff)*60 + mi diff`; trivial = `v & ((1<<26)−1)` (s..µs).
   - SECOND: `diff = (daynr(a)−daynr(o))*86400 + (secs-of-day(a) − secs-of-day(o))` (µs ignored);
     trivial = µs.
   **For DATEV2** (packed u32): YEAR trivial = `v & 0x1FF` (m,d); QUARTER `((m−1)%3)*32 + (v & 0x1F)`;
   MONTH `v & 0x1F` (day); WEEK `(daynr%7)*86400` (no µs); DAY/HOUR/MINUTE trivial 0 (time is 0);
   SECOND trivial 0.
   `daynr` = doris-rs `calc_daynr` (0000-01-01 → 1).
2. CEIL: `diff += (trivial_a > trivial_o)`. FLOOR: `diff −= (trivial_a < trivial_o)`.
3. `delta = diff mod period` (non-negative: `diff>=0 ? diff%p : (diff%p + p)%p`);
   `step = diff − delta + (CEIL && delta != 0 ? period : 0)`.
4. `res = origin + step units` via `date_add_interval<unit>` (QUARTER = `3*step` months): exactly
   doris-rs `add()` semantics — YEAR: year±n, 0..9999, Feb 29 → 28 in a non-leap year; MONTH/QUARTER:
   `months = y*12+m−1 ± n`, `<0` or year>9999 → fail, day clamped to the month's end; WEEK/DAY/HOUR/
   MINUTE/SECOND: seconds arithmetic from day 1 of the month, `daynr ≤ 0 || > 3652424` → fail; the
   origin's µs are kept (results carry the **origin's** sub-unit fields, e.g. `month_ceil(x, 1,
   '2022-01-10')` lands on day 10, clamped to month end: `quarter_ceil('2023-06-15 08:30:45', 1,
   '1999-12-31')` = `2023-06-30 00:00:00`).
5. Failure → OUT_OF_BOUND (-218) with
   - 1 arg: `Operation {name} of {date} out of range` (`year_ceil('9999-12-31')`, planned as
     DTV2(0) → `Operation year_ceil of 9999-12-31 00:00:00 out of range`)
   - `(date, origin)`: `Operation {name} of {date}, {origin} out of range`
     (captured: `Operation year_ceil of 9999-12-31 00:00:00, 2000-01-01 00:00:00 out of range`)
   - `(date, period)`: `Operation {name} of {date}, {period} out of range`
   - `(date, period, origin)`: `Operation {name} of {date}, {period}, {origin} out of range`, **except**
     when origin is a constant equal to `0001-01-01 00:00:00` → treated as the 2-arg period form and its
     message (:330-334).
   `{name}` is the function name itself (`year_ceil`), not `*_add`.

Week: with the default origin 0001-01-01 (a Monday; `calc_weekday(daynr,false)` = 0) weeks start on
Monday. Worked examples from the suites (all match the algorithm):
`week_floor('2024-01-08 00:00:00.400000', 1, '2024-01-01 00:00:00.500000')` = `2024-01-01 00:00:00.500000`;
`week_ceil('…08 00:00:00.600000', 1, '…01 00:00:00.500000')` = `2024-01-15 00:00:00.500000`;
`day_ceil(dt='2023-06-15 08:30:45', 3, '2023-01-01')` = `2023-06-18`;
`hour_floor('1970-01-01 01:00:10', 1, '1970-01-01 00:00:30')` = `00:00:30`;
`quarter_floor(dt, '2000-02-01')` (2-arg origin) over 2023-06-15 = `2023-05-01`.

Quirk (unlikely to matter): the optimized 1-period `hour/minute/second_floor` on a **DATEV2** value
writes nothing (garbage result); the FE never plans those.

## 2. `milliseconds_add` (and `_sub`)

`function_date_or_datetime_computation.h:76-133` (`date_time_add` + `ADD_TIME_FUNCTION_IMPL`), wrapper
`FunctionDateOrDateTimeComputation` (:858-985). Registered for DATETIMEV2 (and TIMESTAMPTZ) only
(`function_date_or_datetime_computation.cpp:79-80,134-135`). FE `MilliSecondsAdd.java`:
`(DATETIMEV2(6), BIGINT) -> DATETIMEV2(6)` (argument cast to scale 6).

`−delta`. Algorithm (`date_add_interval<MILLISECOND>`, `core/value/vdatetime_value.cpp:2524-2566`):

## 3. `day_hour_add`, `day_second_add`, `minute_second_add`, `second_microsecond_add` (and `_sub`)

`function_date_or_datetime_computation.h:141-363` (`AddUnionTypeImpl`), `_sub` :463-488
(`SubtractUnionIntervalImpl`), registered for DATETIMEV2/TIMESTAMPTZ only (`.cpp:108-128,277-286`).
FE: `DayHourAdd`/`DaySecondAdd`/`MinuteSecondAdd`: `(DATETIMEV2(WILDCARD), VARCHAR) -> DATETIMEV2(same)`;
`SecondMicrosecondAdd`: `(DATETIMEV2(6), VARCHAR) -> DATETIMEV2(6)`. SQL
`date_add(x, INTERVAL '<s>' DAY_SECOND)` becomes `day_second_add(x, '<s>')`; a DATE argument is cast to
DATETIMEV2 by the FE (the suite's `test_date` rows print with a time part).

NULL: same as the add family (null rows skipped, OR of null maps).

### Interval string parsing (`get_interval_value` :257-345, `extract_time_values` :186-237)
Parts: DAY_HOUR = [day, hour]; DAY_SECOND = [day, hour, minute, second]; MINUTE_SECOND =
[minute, second]; SECOND_MICROSECOND = [second, microsecond] with `transform_msec = true`.
1. Trim **spaces only** (`StringRef::trim`, `core/string_ref.cpp:27-42`) from both ends.
2. Skip leading spaces/tabs; if the next char is `-`, the **whole** interval is negative; skip it.
3. Skip to the first digit (any non-digit chars are separators: `' 1  1 : 1 : 1 '`, `'1 -1:1:1'` (the
   inner `-` is just a separator → positive 1 1:1:1), `'xx 10'` all parse).
4. For each of `count` parts: read digits into an i64 (`value > (LLONG_MAX−10)/10` before a digit →
   error); `msec_length = 6 − ndigits`; skip non-digits. If the string ends before all parts are read,
   the parts read so far are **right-aligned** (leading parts become 0): `'1'` DAY_HOUR → 0 days 1 hour;
   `'1 2'` DAY_SECOND → 0 d 0 h 1 m 2 s; `'1 xx:00:01'` → 1,00,01 → 0 d 1 h 0 m 1 s.
5. If `transform_msec` and `0 < msec_length ≤ 6`, the **last** part is scaled by `10^msec_length`
   (uses the digit count of the last part read): `'1.1'` → 1 s 100000 µs; `'1.12'` → 120000 µs;
   `'1'` SECOND_MICROSECOND → right-aligned [0, 1] → 100000 µs; `'1.1234567'` (7 digits) → 1234567 µs
   unscaled; `'1.123423432'` → 123423432 µs (adds 123.423432 s).
6. Error iff characters remain after all parts were read (`cur != end`, i.e. too many digit groups) or
   no digit at all. Trailing non-digits are skipped (`'-1 -1:1:1xxx'` is fine).
   Error → INVALID_ARGUMENT: `Operation day_second_add of {trimmed string} is invalid`.

`_sub`: trim; if it starts with `-` drop that char, else prepend `-`; then the add path (so messages
always say `*_add`, with the negated string).

### Applying it (`date_add_interval<UNION>`, cpp:2524-2566)
One signed total: `us = t.us + sign*interval.us`; `secs = (day−1)*86400 + h*3600 + mi*60 + s +
sign*(D*86400 + H*3600 + M*60 + S) + us/1e6` (truncating), etc. — the same seconds/µs arithmetic as
`milliseconds_add`. (Fields are u64; `sign*` wraps like two's complement — use wrapping i64 math.)
Result out of 0000-01-01..9999-12-31 → OUT_OF_BOUND `Operation day_second_add of {date}, {delta
string as given (untrimmed; negated for _sub)} out of range`.

Expected values (test_dateadd_with_other_timeunit; columns `test_datetime DATETIME(6)` = {`2025-10-29
10:10:10`, `2025-10-24 01:02:03.123456`}, `test_date DATE` cast to DTV2):
`"1 1:1:1"` → `2025-10-25 02:03:04.123456`; `"-1 -1:-1:-1"` on `2025-10-29` → `2025-10-27 22:58:59`;
`"1 -10"` DAY_HOUR → +1 d 10 h; `'xx 10'` DAY_HOUR → +10 h; `"1.123423432"` SECOND_MICROSECOND on
`…01:02:03.123456` → `01:04:07.546888`; `"-1.-11233213123"` on `2025-10-24` → `2025-10-23
20:52:45.786877`. BE-evaluated: the column queries and all `testFoldConst`; the plain constant
`qt_sql` ones are FE-folded (but must agree).

## 5. `from_unixtime` (→ `from_unixtime_new` in this cluster)

`date_time_transforms.h:399-512` (`FromUnixTimeImpl`, `FromUnixTimeDecimalImpl`), wrapper
`function_datetime_string_to_string.h:59-245`, registration `function_datetime_string_to_string.cpp`.
FE `FromUnixtime.java`: `(BIGINT[, VARCHAR]) -> VARCHAR`, `(DECIMALV3(18,6)[, VARCHAR]) -> VARCHAR`.

**Name switch:** `SimpleFunctionFactory::get_function` (`simple_function_factory.h:200-203`) appends
`_new` to `unix_timestamp*`/`from_unixtime*` when `TQueryOptions.new_version_unix_timestamp` (field 167)

  valid iff `int + sign(frac) ≥ 0`; **no upper bound** besides `is_valid_date` after the u16 year
  truncation (a year ≥ 65536 wraps — cannot happen within DECIMAL(18,6)'s range? 18 digits → ≤ 10^12 s ≈
  year 33658, fine, so `is_valid_date` catches it). Civil time from cctz + `us = frac` (scale 6).
- NULL: default implementation (null in → null out) with `need_replace_null_data_to_default` (null rows
  are computed on value 0 — harmless).
- Invalid value → **error, not NULL**: INVALID_ARGUMENT
  `Operation from_unixtime_new of {v}, {format} is invalid`; for the decimal form `{v}` is
  `"{int}.{frac}"` with `frac` printed as a plain integer (no zero padding: 1.000005 → `1.5`).
  Captured: `Operation from_unixtime_new of 253402300800, %Y-%m-%d %H:%i:%s is invalid`.

### Format argument (`open`, h:86-133)
- No format argument: BIGINT → format string `yyyy-MM-dd HH:mm:ss` (output `YYYY-MM-DD hh:mm:ss`;
  the error text shows that string: `Operation from_unixtime_new of 253402300800, yyyy-MM-dd HH:mm:ss
  is invalid`); DECIMAL → `%Y-%m-%d %H:%i:%s.%f` (output `…hh:mm:ss.ffffff`). Both the 1-arg plan
  `from_unixtime(BIGINT)` and the 2-arg `from_unixtime(BIGINT, VARCHAR(17) '%Y-%m-%d %H:%i:%s')` occur.
- The format must be a constant (else `InvalidArgument "The second parameter of the function
  from_unixtime must be a constant."`); NULL constant or length > 128 after trimming spaces →
  marked invalid → at execute: INVALID_ARGUMENT `Operation from_unixtime of invalid or oversized format
  is invalid` (thrown even for zero rows).
- Format trimmed of spaces; then `string_to_impl` (`date_format_type.h:325-341`) picks a fast path for
  exactly `yyyyMMdd`/`%Y%m%d`, `yyyy-MM-dd`/`%Y-%m-%d`, `yyyy-MM-dd HH:mm:ss`/`%Y-%m-%d %H:%i:%s`,

## 6. `unix_timestamp` (→ `unix_timestamp_new`)

`function_other_types_to_date.cpp:655-929`; registration :1501-1516. FE `UnixTimestamp.java`:
`() -> BIGINT`; `(DATEV2) -> BIGINT`; `(DATETIMEV2(s)) -> DECIMALV3(12+s, s)`;
`(VARCHAR|STRING, VARCHAR|STRING) -> DECIMALV3(18,6)`. A 1-arg string literal is planned as
`unix_timestamp(CAST(str AS DATETIMEV2(s)))` (s from the text; `'0'`, `'2023/04/31'`,

- `(DATEV2)`: `cctz::convert(civil(y,m,d,0,0,0), session zone)` seconds (= `clock::instant`), then
  `trim_timestamp`: `< 0` → 0; old version also `> INT_MAX` → 0. Result INT32 (old) / INT64 (new).
- `(DATETIMEV2(s))`: `(secs, us)` = instant of the civil second + µs; `trim` (negative or old&&>INT_MAX

- `(str, fmt)`: **own null handling** (null rows skipped; result Nullable iff an arg is). Parse with

  `str_to_date`, datetime target); failure → INVALID_ARGUMENT
  `Operation unix_timestamp of {str}, {fmt} is invalid` (name is always `unix_timestamp`). Then the
  instant in the session zone, trimmed; value = `secs*1e6 + us` (Decimal64 scale 6). No upper limit in
  the new version (9999-12-31 23:59:59 → 253402300799 in UTC).
- NULL for the date forms: default implementation.
- DST: civil → instant uses cctz `pre` (repeated → earlier instant, skipped → pre-transition offset);
  `clock::instant` already does this.

Suite (`fold_constant_date_arithmatic`, all `testFoldConst`, `enable_fold_constant_by_be=false`):
`unix_timestamp('2023/04/31')`, `('1970/01/01 00:00:00')`, `('1970-01-01T00:00:00')`, `('1970-01-01')`,
`('01.Jan.1970','%d.%b.%Y')`, `('1970-01-01','%Y-%m-%d')`, `('0')`. Zones east of UTC make 1970-01-01
negative → `0` / `0.000000`.

## 7. `months_between`

`function_date_or_datetime_computation.h:1415-1523`. FE `MonthsBetween.java`: `(DATEV2, DATEV2[,
BOOLEAN]) -> DOUBLE`; the 2-arg form is built with `Literal.of(true)` as third argument (:50-52), so the
BE always sees 3 args. DATETIME arguments are cast to DATEV2 by the FE (`CAST:DATEV2(SLOT DATETIMEV2(0))`) (time part dropped:
`months_between('2020-02-29 23:59:59', '2020-03-29 00:00:00')` = −1).

- Default NULL handling (any null → null).
- `calc` (h:1496-1516): `diff = (y1−y2)*12 + (m1−m2)`; `dim(x)` = days in x's month (29 for Feb in a
  leap year, `is_leap` as C++: year 0 not leap); if `d1 == dim1 && d2 == dim2` → day term 0, else
  `(d1 − d2) / 31.0`; result `diff + dayterm` (f64).
- `round_off` true → `round(x * 1e8) / 1e8` (C `round`: half away from zero = Rust `f64::round`).
- Examples: (2020-06-30, 2020-07-01, true) → −0.06451613; (1900-01-01, 2100-12-31) →
  −2411.96774194; (2020-02-28, 2021-02-28) → −12; (2020-01-31, 2020-02-29) → −1.
- Output DOUBLE text uses the existing DOUBLE formatter (`.out` shows Java's `-1.0`; the wire has the
  BE's own float text).

## 8. `next_day`

`function_date_or_datetime_computation.h:1524-1614` (`FunctionRelativeDay<false>`). FE `NextDay.java`:
`(DATEV2, STRING) -> DATEV2`, PropagateNullable (default NULL handling).

- Weekday name, uppercased (ASCII), exact match of `MO MON MONDAY TU TUE TUESDAY WE WED WEDNESDAY TH THU
  THURSDAY FR FRI FRIDAY SA SAT SATURDAY SU SUN SUNDAY` → 1..7 (Mon..Sun); no trimming.
  Unknown → `Status::InvalidArgument("Function next_day failed to parse weekday: {s}")` (INVALID_ARGUMENT,
  returned as a status — same text on the wire).
- `delta = (wd − (weekday(d)+1) + 7) % 7`, `0 → 7`; `weekday` = `calc_weekday(daynr, false)` (Mon=0).
  Result `d + delta` days via `date_add_interval<DAY>`; **its failure is ignored** — past 9999-12-31 the
  value stays unchanged (`next_day('9999-12-31','MON')` = `9999-12-31`).
- C++ bug to reproduce: when the **date is constant and the weekday is not**, `dtv` is mutated in place
  and accumulates across rows (row i = date + Σ deltas). Only with a column weekday.
- Suite (`testFoldConst`): `next_day('2020-02-27','SAT')` = 2020-02-29, `('2020-02-29','MON')` =
  2020-03-02, `('2019-02-26','THU')` = 2019-02-28, `('2019-02-28','SUN')` = 2019-03-03.

## 9. `date_format`

`date_time_transforms.h:352-397` (`DateFormatImpl`), wrapper `function_datetime_string_to_string.h`
(same `open`/format rules as §5), `%`-formatter `DatetimeValueUtil::to_format_string_without_check`
(`core/value/vdatetime_value.cpp:3113-3405`). Registered for DATEV2 and DATETIMEV2; FE
`DateFormat.java`: `(DATETIMEV2(WILDCARD), VARCHAR) -> VARCHAR`; a DATEV2 column arrives as
`CAST(slot AS DATETIMEV2(0))` (inlineview_with_project), so the DATEV2 overload is not exercised.

- Default NULL handling (+ null rows replaced with the default value before computing).
- Format: constant, trimmed of spaces, ≤ 128 bytes else error `Operation date_format of invalid or
  oversized format is invalid` (INVALID_ARGUMENT); NULL format constant → same error.
- Fast paths (exact strings, §5): `%Y%m%d`/`yyyyMMdd` → `YYYYMMDD`; `%Y-%m-%d`/`yyyy-MM-dd`;
  `%Y-%m-%d %H:%i:%s`/`yyyy-MM-dd HH:mm:ss`; `yyyy-MM`; `yyyyMM`; `yyyy`. Year always 4 digits.
  (inlineview_with_project: `DATE_FORMAT(date, '%Y%m%d')` on DATEV2 `2020-02-02` → `20200202`.)
- `%` formatter: a `%` that is the last char is literal; `%X` for unknown X writes `X` (so `%%` → `%`).
  `%y` 2-digit year; `%Y` 4-digit; `%d` 2-digit day; `%e` day no pad; `%m` 2-digit month; `%c` month
  no pad; `%H` hour ≥2 digits; `%k` hour no pad; `%h`/`%I` `(h%24+11)%12+1` 2-digit; `%l` same no pad;
  `%i` minute; `%s`/`%S` second; `%f` µs 6 digits; `%p` `AM`/`PM` (`h%24 >= 12`); `%r`
  `hh:mm:ss AM|PM` with 12-hour `(h+11)%12+1`; `%T` `hh:mm:ss`; `%j` day of year 3 digits; `%a`
  `Mon..Sun`; `%W` `Monday..Sunday`; `%b` `Jan..Dec`; `%M` `January..December`; `%D` day + `st/nd/rd/th`
  (11–19 → `th`); `%w` 0=Sunday..6; `%u` week mode 1, `%U` mode 0, `%v` mode 3, `%V` mode 2 (2 digits,
  `DatetimeValueUtil::week` → `calc_week`, year 0 → 0); `%x` year-of-week mode 3, `%X` mode 2 (4 digits).
  For DATEV2 the time fields are 0.
- Length guard: before each format char, if `written + 12 > 112` → failure → INVALID_ARGUMENT
  `Operation date_format of {date}, {format} is invalid` (outputs longer than ~100 bytes fail).
- Suite (`testFoldConst`): `date_format('2020-12-01 00:00:30.01', '%h'|'%I'|'%l'|'%r')` → `12`, `12`,
  `12`, `12:00:30 AM`; same at `12:00:30.01` → `12`, `12`, `12`, `12:00:30 PM`.

## 10. `convert_tz`

`function_convert_tz.cpp:60-319`. FE `ConvertTz.java`: `(DATETIMEV2(WILDCARD), VARCHAR, VARCHAR) ->
DATETIMEV2(same scale)`, PropagateNullable; a string first literal is cast with the text's scale
(`'2021-03-28 02:30:00.00323'` → DTV2(5)).

- Own NULL handling: result null map = OR of the three; Nullable iff any arg is.
- `open`: if both zones are constants → resolved once; a NULL constant zone → every row NULL; an
  unknown name → throw INVALID_ARGUMENT `Operation convert_tz invalid timezone: {name}` **at open**
  (fails exec_plan_fragment even over columns). Non-constant zones are resolved per non-null row with
  the same error.
- Lookup = `TimezoneUtils::find_cctz_time_zone` = doris-rs `clock::find_zone` (case-insensitive tzdata
  names, `Z`, `CST`, `±HH:MM` in −12:00..+14:00 with minutes 00/30/45 cached, then
  `UTC±h[:mm]`/`GMT±h[:mm]`/`±h:mm` normalisation).
- Per row: civil (y..s) looked up in `from`: UNIQUE/REPEATED → `pre` (repeated → **earlier** instant);
  **SKIPPED → the transition instant itself, and µs set to 0**. Then the instant → civil in `to`, µs
  carried. This differs from `clock::instant` for skipped times: need "instant of the transition".
  (With chrono-tz: for a gap civil `c`, `pre = c − off_before`, `post = c − off_after`; the transition
  instant is the unique `t` in `(post, pre]` where the offset changes — binary search on seconds.)
- Result year > 9999 (or a negative year → u16 wrap) → OUT_OF_BOUND
  `Cannot convert {date} from {from.name()} to {to.name()}` where `name()` is cctz's: the tzdata path as
  stored on disk for named zones (`Asia/Shanghai`, `UTC`; `CST` → `Asia/Shanghai`), `Fixed/UTC+08:00:00`
  for offsets (cctz `FixedOffsetToName`; zero offset → `UTC`) — from memory of cctz, unverified here.
- Suite `test_convert_tz` (query_p0): `convert_tz(dt, '+00:00', IF(property_value IS NULL, '+00:00',
  property_value))` over 20 rows of `2024-04-18 23:20:00` (DATETIME → DTV2(0), non-constant third arg
  → per-row path) = unchanged; `set debug_skip_fold_constant=true; convert_tz('2021-03-28
  02:30:00.00323', 'Europe/Paris', 'UTC')` = `2021-03-28 01:00:00.00000` (skipped → transition 01:00
  UTC, µs dropped). Partition-prune `test_convert_tz` (not in our suite list) has only explains plus
  `convert_tz(ts,'UTC','Europe/Paris') = '2021-10-31 02:30:00'` matching 00:30 and 01:30 UTC.

### Time zone database
cctz reads the system tzdata: `TZDIR` or `/usr/share/zoneinfo` (`util/timezone_utils.cpp:40-85`), every
file except `posix/`, `right/`, minus `lmt`, plus `z`→Zulu and `cst`→Asia/Shanghai. The reference image
is Ubuntu 22.04.5 with package `tzdata 2026e-0ubuntu0.22.04.1` (`/usr/share/zoneinfo/tzdata.zi`:
`# version 2026e`). doris-rs uses `chrono-tz 0.10.4`, which bundles **tzdata 2025b**.
- Rule differences 2025b→2026e are possible for a few zones (not checked); none of the suites here use
  an affected zone as far as known (they use fixed offsets, `Europe/Paris` 2021, the session zone).
- **chrono-tz has no DST after 2099** (verified: America/New_York 2099-07-01 → −4h, 2100-07-01 → −5h),
  whereas cctz extends the POSIX TZ rule to year 9999. Any civil↔instant conversion after 2099 in a DST
  zone (convert_tz, unix_timestamp, from_unixtime/from_second, session zone) will differ. Exact match
  needs a TZif reader over the reference's zoneinfo (e.g. the `tzfile`/`tz-rs` crates reading 2026e
  files vendored into the repo) that applies the footer rule, or extending chrono-tz's last rule.
- Fixed offsets are exact.

## Risks / cannot match exactly

- tzdata version skew (2025b vs 2026e) and chrono-tz's 2099 cutoff (above).
- `next_day` const-date accumulation and silent overflow — reproducible, just odd.
- `from_unixtime` decimal error text prints the fraction unpadded.
- cctz zone `name()` strings in `convert_tz` errors are from memory.
