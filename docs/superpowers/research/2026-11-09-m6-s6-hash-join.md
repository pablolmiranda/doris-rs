# Doris 4.1.5 BE HASH JOIN — semantics, layout, and output order (for doris-rs)

Paths are relative to `be/src/` unless noted. Abbreviations: HT = `exec/common/hash_table/join_hash_table.h`,
PI = `exec/operator/join/process_hash_table_probe_impl.h`, BS = `exec/operator/hashjoin_build_sink.{h,cpp}`,
PO = `exec/operator/hashjoin_probe_operator.cpp`, JP = `exec/operator/join_probe_operator.{h,cpp}`.

## 0. Core data structures (needed for everything below)

- **Build block**: the sink starts the build block with ONE mock row (row 0) of default values
  (BS.cpp:834-844, `create_same_struct_block(1)`), then appends every incoming build block in arrival
  order (`merge_ignore_overflow`, BS.cpp:846-865). At eos the merged block becomes `shared_state->build_block`
  (BS.cpp:868-878). **Real build row k (0-based arrival order across all build blocks) has index k+1.**
- For LEFT_OUTER / FULL_OUTER / ASOF_LEFT_OUTER, every build column is made nullable and row 0's null flag
  is set to 1 (BS.cpp:595-617). So build index 0 = "all-NULL build row", used for null extension.
- **Hash table** = `first[bucket_size+1]` + `next[num_rows]` (HT:52-73). Build insertion (HT:89-101):
  `for i in 1..rows: next[i] = first[bucket[i]]; first[bucket[i]] = i;` → **head insertion**: a bucket chain
  goes from the HIGHEST row index to the lowest. Rows with a NULL key go to the extra bucket `bucket_size`
  (hash_map_context.h:82, 814); that bucket is cleared (`first[bucket_size]=0`) unless `keep_null_key`
  (HT:97-99). `keep_null_key` = single-key `<=>` join, or NULL_AWARE_* with other conjuncts (BS.h:241-257).
- Chain walk compares keys with `==` (HT:238-243, 311, 330, 385); colliding different keys are skipped,
  so **for one probe key the matches are emitted in descending build row index = reverse build arrival order**.
  Direct-mapping (small int range) variant: one bucket per key value, same head-insertion order (HT:59-61).
- Probe side: per probe block, `bucket_nums[i]` → `first[bucket]` (HT:231-235, PI:246-248). Probe rows with
  a NULL key (external null map, any key column NULL) hash to `bucket_size` → normally chain 0 = no match.

## 1. Output layout

**Intermediate block** = slots of `vintermediate_tuple_id_list` in order (JP.cpp:54-62, JP.cpp:121-123).
Layout is positional: `[all left-child slots][all right-child slots][mark slot if is_mark]`
(`_right_col_idx`, PO:618-621; type check PO:593-673). Exceptions (FE PhysicalPlanTranslator.java:1895-1915):
- LEFT_SEMI / LEFT_ANTI / NULL_AWARE_LEFT_ANTI with no other_join_conjuncts and (hash conjuncts XOR mark
  conjuncts) → intermediate = left slots only (+ mark). NULL_AWARE_LEFT_SEMI always gets both sides.
- RIGHT_SEMI / RIGHT_ANTI with no other conjuncts (and no mark conjuncts) → right slots only;
  BE sets `_right_col_idx = 0` (PO:618-621).
- With other conjuncts, semi/anti have both sides; after filtering, LEFT_SEMI/ANTI/NAAJ keep only the first
  `_right_col_idx` (left) columns (PI:994-1000); RIGHT_SEMI/ANTI emit left columns as dummy constants (PI:1069-1073).

**hash_output_slot_ids**: flags computed per *child* slot id (left child row_desc, build child row_desc)
(PO:551-567; BS.cpp:800-813). Only flagged columns are materialized; unflagged ones become a ColumnConst of the
type's default (`mock_column_size`, PI:59-67, 144-146, 216-218). NB: empty list ⇒ nothing flagged (code
does not implement "empty = all", despite comments); Nereids always populates it. Pruned columns are never
referenced downstream, so doris-rs may fill them with anything (NULL is simplest).

**After join**: `_conjuncts` (node conjuncts) are evaluated on the intermediate block (PO:390-405;
operator.cpp:250-251 prepares them against `intermediate_row_desc()` which for joins is the
intermediate tuple, JP.h:68-70). Then generic `do_projections`: intermediate_projections_list[i] then
`projections` into `output_tuple_id` (operator.cpp:206-266, 327-354), then limit (`reached_limit`, PO:404).
`_build_output_block` is just a swap (JP.cpp:75-83) — no join-specific projection logic.

**Nullability** (FE translator lines ~1977-1994; BE PO:652-657):
- LEFT_OUTER, ASOF_LEFT_OUTER: right slots nullable. Build columns converted to nullable, row 0 NULL (BS.cpp:595-617).
- RIGHT_OUTER: left slots nullable; probe columns converted to nullable at push (PO:447-450); unmatched build
  rows get `insert_many_defaults` (= NULL) for left columns (PI:1076-1081).
- FULL_OUTER: both.

**Mark join**: mark slot = LAST slot of the intermediate tuple, must be `Nullable(Boolean)` (PO:600-616,
JP.cpp:64-72). Value per probe row: TRUE / FALSE / NULL (see §2.6). Mark joins emit **every probe row exactly
once** (with its mark); filtering on the mark happens later (node conjuncts or parent).

## 2. Semantics per join op

General: EQ never matches NULL (null-key rows sit in bucket `bucket_size`, cleared). EQ_FOR_NULL:
treated as `<=>` only if one side is nullable (BS.cpp:753-762, PO:475-482). Single key `<=>`: keep the null
bucket; null keys are normalised to default value so all NULLs compare equal (BS.h:233-236, PI:239-244,
string keys → empty StringRef hash_map_context.h:380-394). Multi-key: `<=>` keys are serialized with a null
flag into the key (`_serialize_null_into_key`, BS.cpp:764-773); plain-EQ keys contribute to the external null
map → if any EQ key is NULL the row never matches.

Other join conjuncts: evaluated on the (probe,build) candidate rows of the intermediate block; NULL counts as
false (`execute_conjuncts` with accept_null=false, PI:905-911; vexpr_context.cpp:293-322). Candidates come
from `_find_batch_conjunct` (HT:321-372): all key matches in chain order, plus for LEFT_OUTER/FULL_OUTER/
LEFT_SEMI/LEFT_ANTI/NA*/ASOF_OUTER a trailing `(probe, build=0)` sentinel per probe row (HT:343-356).
`_last_probe_match` (reset per probe block, PO:110-117) carries "this probe row already produced a hit" across
batches.

2.1 **INNER**: one row per (probe, matching build) (HT:375-426). Other conj: keep passing pairs (`finalize_block_with_filter`).
2.2 **LEFT_OUTER**: matches; if none, one row with build index 0 (NULLs) (HT:399-411). With other conj
   (PI:919-947): keep pairs passing the conjunct; the sentinel (p,0) is kept iff no pair of p passed →
   exactly one NULL-extended row for a probe row whose matches all fail. Null probe key → NULL-extended.
2.3 **RIGHT_OUTER**: probe phase emits matched pairs only, marking `visited[b]=1` (HT:389-394). With other
   conj, `visited[b] |= passed` and only passing pairs output (PI:984-988). After all probe input:
   every build row with `!visited` (incl. NULL-key build rows) with NULL left columns (HT:200-225, PI:1008-1086).
2.4 **FULL_OUTER**: LEFT_OUTER behaviour for probe rows + RIGHT_OUTER tail. With other conj visited is set
   only for kept rows that passed (PI:940-945).
2.5 **LEFT_SEMI / LEFT_ANTI** (no other conj, not mark): `_find_batch_left_semi_anti` (HT:293-319): one row per
   probe row if (semi) found / (anti) not found. Null probe key ⇒ no match ⇒ semi drops, **LEFT_ANTI keeps it**.
   With other conj (PI:948-978): semi outputs p once at its first passing pair; anti outputs p (via sentinel)
   iff no pair passed. Output columns = left only.
   **NULL_AWARE_LEFT_ANTI (non-mark)**: if the build side has ANY NULL key → result is empty
   (short-circuit, BS.h:219-227 + BS.cpp:323-331; applies even with other conjuncts). Else null probe keys
   are skipped (HT:302-307) — except when the build side is empty: then every probe row, NULL key or not,
   is output (HT:109-114, 245-265). With other conj: matches + null-bucket rows (HT:428-496); a NULL probe key is
   paired with every build row 1..n (PI:631-652); p kept iff no pair passed other conj.
   NULL_AWARE_LEFT_SEMI non-mark without other conj is unsupported (falls to the throw at HT:168).
2.6 **Mark joins** (`do_mark_join_conjuncts`, PI:741-892). Candidates: for null-aware ops, or LEFT_SEMI/ANTI
   without mark conjuncts (and no other conj) only the first match + sentinel (HT:121-139); otherwise all matches + sentinel.
   Mark starts TRUE/non-null for each candidate (PI:148-156), then is ANDed (three-valued) with mark_join_conjuncts
   (vexpr_context.cpp:324-370).
   - non-null-aware: `null &= (build!=0)` (PI:800-806).
   - null-aware (NAAJ/NALSJ): `value = build!=0`; without other conj: `null |= probe key is NULL`,
     and `null |= (build==0 && build side has a NULL key)` (PI:774-799); with other conj: null = `null_flags`
     (pair came from the build null-bucket or a NULL probe key) (PI:783-786).
   - other conj: `value &= !null & other`; `null &= other` (PI:808-826).
   - Per probe row (PI:846-862): first candidate with value=TRUE ⇒ emit TRUE; else at the sentinel emit FALSE,
     or NULL if any candidate was NULL. Anti: flip value (NULL stays NULL) (PI:881-886).
   - Result (semi): TRUE if some match passes; else NULL if (null-aware and (probe key NULL or build has NULL key))
     or any candidate evaluated NULL; else FALSE. Empty build side + null-aware ⇒ FALSE (anti ⇒ TRUE) even for a
     NULL probe key (`ignore_null_map`, PI:609-614; HT:109-114).
   - Nereids: when there are no hash conjuncts the mark conjunct becomes the eq key and LEFT_ANTI/LEFT_SEMI are
     renamed NULL_AWARE_* (fe .../PhysicalPlanTranslator.java:1781-1799); for null-aware ops mark_join_conjuncts is empty (PO:520-524).
2.7 **RIGHT_SEMI / RIGHT_ANTI**: probing only sets `visited` (HT:267-291; with other conj PI:979-983), the
   probe phase outputs nothing (PI:594-597, 990-992). At the end: SEMI emits visited build rows, ANTI emits unvisited
   (incl. NULL-key build rows) (HT:200-225).
2.8 **ASOF_LEFT_INNER / ASOF_LEFT_OUTER** (brief): eq keys hash as usual; `match_condition` = `probe_expr OP build_expr`
   (OP ∈ GE, GT, LE, LT) (BS.cpp:779-791, PO:529-539). Build: per distinct key, sort (build value, row) with
   **unstable pdqsort** (exec/common/join_utils.h:255-262). Probe: per probe row, at most one build row: GE → max
   build ≤ probe, GT → max < probe, LE → min ≥ probe, LT → min > probe (join_utils.h:311-320). NULL key/NULL asof value
   ⇒ no match; OUTER ⇒ NULL-extended (PI:262-490). Only DATEV2/DATETIMEV2/TIMESTAMPTZ asof columns. No other conjuncts
   (FE sends none; PI:603-606). Ties on the asof value pick an arbitrary row because the sort is unstable.

## 3. Key comparison

- Hash method by key types (hash_key_type.h:104-152): one numeric key ⇒ raw fixed-width integer of the value's bytes
  (`int32_key`/`int64_key`/`int128_key`…); several fixed keys ⇒ packed fixed bytes + null bitmap; strings ⇒
  `StringRef` (bytes, length+memcmp); otherwise serialized bytes. **All comparisons are bitwise.**
  ⇒ DOUBLE/FLOAT: `-0.0` ≠ `0.0`; NaN matches only a NaN with the identical bit pattern. No normalisation
  anywhere in exec/common/hash_table.
- Type check: build and probe key expr types must be equal up to nullability or the BE errors out
  (BS.cpp:734-746). So INT vs BIGINT must be cast by the FE (it does, inside eq_join_conjunct.left/right).
  **Your "13 vs 15" is TPrimitiveType CHAR(13) vs VARCHAR(15)** (gensrc/thrift/Types.thrift:74-76), not INT/BIGINT.
  Both are `DataTypeString`, whose `equals` is just a typeid check (core/data_type/data_type_string.cpp:58-60), so no
  cast is needed and the bytes are compared as-is. The join adds no CHAR padding/trimming logic; CHAR values
  compare equal iff their stored bytes are equal.
- DECIMAL keys compare by the raw unscaled integer (both sides have the same type after FE casts). DATEV2/DATETIMEV2 compare as raw uint32/uint64.

## 4. OUTPUT ROW ORDER (exact)

Probe blocks are processed in arrival order; within a block, `probe_index` increases monotonically and resumes
mid-chain across batch boundaries (`probe_idx -= (build_idx != 0)`, HT:370, 424; state kept in `_probe_index`,
`_build_index`, `_probe_visited`, `_last_probe_match`). `Block::filter` preserves order. Therefore:

1. **Probe phase**: rows come out in probe-row order. For one probe row with several matches, the build rows come out in
   **descending build index = reverse of build arrival order** (last-arrived build row first), because of head
   insertion (HT:92-96). This holds across multiple build blocks (they are concatenated first, BS.cpp:860) and for
   direct mapping. With other conjuncts the survivors keep that order. LEFT_OUTER/FULL unmatched probe rows appear in
   their probe position (the sentinel comes after the row's matches). Semi/anti/mark: one row per probe row, in probe order.
   Doris-rs model: `for p in probe_rows: for b in build_rows.reversed() if key(b)==key(p): emit(p,b)`.
2. **Tail** (RIGHT_OUTER, FULL_OUTER, RIGHT_SEMI, RIGHT_ANTI): after probe eos (PO:278-301), `iterate_map` scans
   `visited` from index 1 upward (HT:200-225, `iter_idx = 1` HT:508) ⇒ **build arrival order**. RIGHT_SEMI/ANTI emit
   rows ONLY in this tail; RIGHT/FULL OUTER emit matched pairs during probing and unmatched build rows in the tail.
3. NULL-aware with other conjuncts: the null-bucket chain is also descending; a NULL probe key enumerates build rows
   ascending (PI:637-641). Only the per-probe-row mark/keep decision depends on this, not the output order.
4. **batch_size** (FE default **8160**, fe/.../qe/SessionVariable.java:1387; HT default 4064 is overwritten in
   `prepare_build`, HT:58) only caps each output chunk (HT:329, 384, 207). It never reorders rows.
5. Row 0 is a dummy that is never inserted into a chain (HT:92 starts at 1) and never emitted by `iterate_map`.
   It only appears as the "no match" sentinel (NULL build columns for LEFT/FULL).
6. Outside the join operator: Doris may put local exchanges or several pipeline tasks per instance in front of the
   join (e.g. `required_data_distribution`, BS.h:136-147). Those change probe/build arrival order, not the rules above.

## 5. Empty build side and short-circuits

`init_short_circuit_for_probe` (BS.cpp:318-339). "Empty" means the build block has only the mock row.
- `short_circuit_for_probe` (if not a mark join): (NAAJ and build has a NULL key) OR (empty build and op ∈ {INNER, LEFT_SEMI,
  RIGHT_OUTER, RIGHT_SEMI, RIGHT_ANTI, ASOF_LEFT_INNER}) ⇒ `pull` returns eos right away (PO:192-196) and
  `need_more_input_data` is false (PO:408-413): **the probe child is never pulled**, so probe-side errors stay hidden
  (unless the scan already started — scheduler-dependent).
- `empty_right_table_need_probe_dispose`: empty build, no other conjuncts, not mark, op ∈ {LEFT_OUTER, FULL_OUTER,
  LEFT_ANTI, ASOF_LEFT_OUTER} ⇒ each probe block passes straight through with all right columns NULL (none for
  LEFT_ANTI), then node conjuncts are applied (PO:199-234). Same result as the general path.
- All other cases (other conjuncts, mark joins, NAAJ/NALSJ) go through the normal path. An empty build gives
  sentinel-only candidates; for null-aware ops every probe row is emitted with build=0 (HT:109-114).
- NAAJ non-mark with a NULL build key does not build the hash table at all (BS.h:219-227).
- The `left_semi_direct_return` optimisation (LEFT_SEMI, single key, no other conjunct, not mark, session var default true,
  local IN runtime filter; BS.cpp:283-292, BS.h:164-170, PI:492-507) emits every probe row unchanged, relying on the
  IN runtime filter already applied below. The result is the same as a normal semi join.

## 6. Shared hash table (broadcast)

`_use_shared_hash_table = is_broadcast_join && enable_share_hash_table_for_broadcast_join` (default true,
SessionVariable.java:2338; BS.cpp:796-799). Only the task with `task_idx == 0` builds (BS.cpp:58-62). The other tasks
wait, then copy the hash-table pointer (BS.cpp:882-907), and `build_block` is shared. **Every task sees the whole
broadcast build side.** `visited` lives inside the shared hash table, so broadcast is only correct for joins without a
build-side tail; Nereids does not broadcast RIGHT_OUTER/FULL/RIGHT_SEMI/RIGHT_ANTI. NAAJ requires NOOP distribution
(BS.h:137-138). Shuffled (PARTITIONED/BUCKET_SHUFFLE/COLOCATE) joins: each instance builds from its own partition.
For doris-rs: each fragment instance builds its own table from the build exchange input. Same results.
